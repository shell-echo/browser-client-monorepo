# Deployment and delivery

[Project home](../README.md) · [Applications](applications.md) · [Reinit](reinit.md) · [Testing](testing.md)

This guide covers the default root-path templates. Choose hosting and credentials in the derived business project. Building or packaging does not deploy a service or submit an extension to a store.

## Build a registered instance

```sh
pnpm install --frozen-lockfile
pnpm app doctor
pnpm app build web
pnpm app build admin
pnpm app build extension
```

Substitute a custom instance ID, for example `pnpm app build portal`. `pnpm build` builds the current registered combination; an empty combination has no application artifact. Workspace builds need the root lockfile, shared packages and integration scripts. Run `pnpm check`, `pnpm audit:security` and affected browser acceptance before delivery.

## Web: a Next.js Node service

The default Web build produces `apps/<id>/.next` for Next.js server deployment:

```sh
pnpm app build web
pnpm app start web
```

The instance start command binds to localhost and its registered port. For a Node host, install the frozen workspace in a matching environment, build the chosen instance, supervise its start command, and place an HTTPS reverse proxy in front of it. A Next.js provider can instead use the instance as its application root while resolving workspace dependencies and the lockfile from this repository. See [Next.js deployment options](https://nextjs.org/docs/app/getting-started/deploying).

`.next` alone is not a generic static-file deployment. Standalone output, static export, containers and provider-specific adapters have different requirements. Persist required framework changes in the reinit integration adapters and validate the actual chosen output before depending on it.

## Admin: static hosting with an SPA fallback

Publish the **contents** of `apps/<id>/dist` after `pnpm app build <id>`. Vite preview is a local verification server, not the production host. See [Vite deployment](https://vite.dev/guide/static-deploy.html).

The default history router needs `index.html` for `/login`, `/dashboard` and other application routes. Missing files under `/assets/` should return 404. A root-path Nginx site can use:

```nginx
root /srv/admin/dist;

location /assets/ {
    try_files $uri =404;
    add_header Cache-Control "public, max-age=31536000, immutable";
}

location / {
    try_files $uri $uri/ /index.html;
    add_header Cache-Control "no-cache";
}
```

Configure TLS and the hostname on the actual host. Verify direct navigation and reload at `/login`, `/dashboard` and an unknown route after deployment. Missing JavaScript must not receive an HTML fallback; route recovery relies on genuine chunk failures.

### Subdirectory deployments

The supplied templates target `/`. Hosting at `/admin/` requires coordinated Vite `base`, React Router `basename`, links and public-asset URLs. Changing only one is insufficient. Persist framework changes in `scripts/lib/integrate.mts` / `scripts/lib/tooling.mts`, update the instance's browser assertions to exercise the prefix, and validate the hosting layout. A direct edit to generated `vite.config.ts` alone is regenerated by reinit.

## Environment inputs

Keep real `.env*` files private in `apps/<id>/`. Only sanitized `.env.example` / `.env.<name>.example` belongs in Git. The starter currently needs no business API configuration.

`NEXT_PUBLIC_*` and `VITE_*` are public client inputs and can be embedded during builds; changing the host environment later does not replace emitted client values. Keep credentials and private signing keys on the server or publishing system. Extension packages are downloadable client code too.

Application `.env*` files already participate in build-cache inputs. Add future build-affecting server variables to `turbo.json`'s `build.env`, document them and rebuild when values change. Supply runtime server configuration to the supervised Next.js process. Add validation when the business project introduces required variables.

## Extension: verified production ZIP

```sh
pnpm app build extension
pnpm extension:package extension --dry-run
pnpm extension:package extension

# Additional Extension instances use their own IDs and manifest versions:
pnpm app build addon
pnpm extension:package addon
```

Packaging reads a previously built **`dist`**, validates production Manifest V3 output, checks its version against `manifest.config.ts`, rejects development clients, private environment files and symbolic links, and writes a ZIP with `manifest.json` at its root. Stop editing/building while packaging. Rebuild after source changes: packaging does not prove that every UI source file was used by an earlier build.

Artifacts and per-file SHA-256 receipts go into a new private `.reinit/releases/<id>-<timestamp>-<nonce>/` directory. Existing deliveries are never overwritten. Sorted ZIP entries and fixed metadata make identical inputs reproducible. The standard ZIP store method is uncompressed; inputs are bounded to 128 MiB and 10,000 files to bound local memory. Larger business extensions need a separately validated streaming packager.

The store version is `version` in `manifest.config.ts`; the workspace package's initial `0.0.0` is not the store version. Use one to four numeric components, each at most 65535, without leading zeros, and not all zero. Increment it for later submissions. `dist-dev` and ordinary UI preview are development tools, not submission artifacts.

Before submitting, load production `dist` in Chrome and Edge and check popup, settings and permissions. Listings, privacy disclosures, screenshots, publisher verification and upload credentials belong to publishing. Follow the [Chrome Web Store guide](https://developer.chrome.com/docs/webstore/publish) and [Microsoft Edge guide](https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/publish-extension). No automatic store upload is configured.

## Reinit and delivery records

Reinit preserves business sources, manifests, browser configuration, packaging tools and this guide. Root axe tooling participates in compatible online dependency planning and recorded offline replay. Additional audit paths remain in preserved instance browser configuration. Browser gates, including accessibility, run before replacement.

`.reinit/releases/` is separate from framework replacement and ordinary successful-workspace cleanup. Receipts, validation reports and failure scenes remain available. A dependency refresh or a new build does not publish an artifact by itself.
